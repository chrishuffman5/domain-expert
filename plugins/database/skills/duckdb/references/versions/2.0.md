# DuckDB 2.0 LTS

This reference covers DuckDB 2.0 (codename "Cinnamon Teal"; the GitHub release and branch call it "Cyanoptera"), released **October 21, 2026** with nearly 20,000 commits since 1.5. It is the current release and the current **LTS** line. Headline changes: the Quack client-server protocol plus `CONNECT`, asynchronous I/O, first-class `VARIANT` with shredding, CLI agent mode, the PEG parser as default, custom extension repositories and C API v2, triggers, many SQL dialect additions, and a new default storage format (version 69) that **DuckDB 1.x cannot read**.

## Storage Format Compatibility (read this first)

> Source: https://duckdb.org/docs/2.0/internals/storage.html
> Source: https://duckdb.org/docs/2.0/operations_manual/migration.html
> Source: https://duckdb.org/docs/2.0/sql/statements/attach.html

**The rule:** DuckDB 2.0 creates new database files in storage version **69**. Every DuckDB before 2.0 fails to open them:

```
IO Error: Trying to read a database file with version number 69, but we can only read versions between 64 and 68.
```

- DuckDB 1.0 through 1.5 write storage version **64** by default (65-68 exist only if you opted in with an explicit storage version). Do not describe 68 as the 1.5 default.
- 2.0 reads **and writes** existing older files without upgrading them: they keep their version and stay readable by 1.x. The hazard is files 2.0 **creates** (including new attachments, exports re-imported by 2.0, and DuckLake metadata files a 2.0 client opens -- see DuckLake below).
- Forward compatibility is best-effort only; backward compatibility (newer reads older) has held since 0.10.

| Storage version | Written by |
|---|---|
| 69 | v2.0.x |
| 68 | v1.5.x (opt-in) |
| 67 | v1.4.x (opt-in) |
| 66 | v1.3.x (opt-in) |
| 65 | v1.2.x (opt-in) |
| 64 | v0.9, v0.10, v1.0, v1.1 -- and the 1.0-1.5 default |

**Stay readable by 1.x** -- the value is the *minimum* DuckDB version that must be able to read the file:

```sql
ATTACH 'shared.duckdb' (STORAGE_VERSION 'v1.5.0');          -- per new file
SET storage_compatibility_version = 'v1.5.0';               -- session/config default (2.0 default: 'latest')
```

```bash
duckdb my.db -storage-version v1.5.6 -c "CREATE TABLE t (x INT);"
```

```python
duckdb.connect("shared.duckdb", config={"storage_compatibility_version": "v1.5.0"})
```

Encrypted databases need storage version 1.4.0 or later.

**Check a file's version** -- never trust the header (2.0-format files store `999` after the magic bytes, and 1.5.5 and earlier report 999 instead of 69; 1.5.6 reports the real version):

```sql
ATTACH 'file.db' AS file_db (READ_ONLY);
SELECT database_name, tags['storage_version'] FROM duckdb_databases();
```

**Convert:**

```bash
# Upgrade a file to the 2.0 format: export with the OLD binary, import with 2.0 (target folder empty)
/older/duckdb mydata.old.db -c "EXPORT DATABASE 'tmp'"
/newer/duckdb mydata.new.db -c "IMPORT DATABASE 'tmp'"
```

```sql
-- Downgrade: copy into a file pinned to an older storage version (writer must be >= 1.2.0)
ATTACH 'file1.db';
ATTACH 'converted_file.db' (STORAGE_VERSION 'v1.0.0');
COPY FROM DATABASE file1 TO converted_file;
```

**Mixed-version deployments:** one 2.0 process creating a file in a shared directory makes it unreadable to every 1.x process. Before the first 2.0 process writes, confirm every reader is on 2.0 or pin `storage_compatibility_version`.

**What the v2.0.0 format adds:** lazy column-metadata loading (wide tables and large indexes open faster with less memory), `DICT_FSST` string compression on by default, more compact delete storage, stronger corruption validation on read.

## Breaking Changes and Revert Switches

> Source: https://duckdb.org/docs/2.0/operations_manual/migration.html
> Source: https://duckdb.org/docs/2.0/sql/functions/lambda.html
> Source: https://duckdb.org/docs/2.0/sql/peg_parser.html

| Change in 2.0 | Symptom | Fix / revert |
|---|---|---|
| Storage version 69 default | 1.x readers fail with the IO Error above | `STORAGE_VERSION` / `storage_compatibility_version` / `-storage-version` |
| Single-arrow lambdas disabled | `x -> x + 1` errors | Rewrite as `lambda x : x + 1`; bridge `SET lambda_syntax = 'enable_single_arrow';` (flag and syntax removed in 2.1) |
| PEG parser default | Parse errors on previously accepted SQL; silent result changes below | `INSTALL AND LOAD legacy_parser; SET enable_legacy_parser = true;` (best-effort bridge; report regressions on GitHub) |
| `~` / `!~` partial match (PostgreSQL semantics) | `'abc' ~ 'b'` is now `true` (was `false`) | Anchor patterns, or `SET regex_match_operator_semantics = 'full';` (deprecated) |
| Factorial `!` binds tighter | `2 * 3!` = 12 (was 720) | Parenthesize: `(2 * 3)!` |
| `X'..'` / `B'..'` literals | Now BLOB / BITSTRING, not VARCHAR | Cast explicitly |
| Any error aborts an explicit transaction | Later statements fail with "transaction is aborted" until `ROLLBACK` | `SET default_transaction_invalidation_policy = 'SYNTACTIC_ERRORS_DO_NOT_INVALIDATE';` |
| Integer `//` and `%` by zero error | Was NULL | `TRY(1 // 0)` per expression; `SET error_on_division_by_zero = false;` globally. `1 / 0` still returns `inf` |
| MERGE INTO multi-match errors | `MERGE INTO command cannot affect the same target row more than once` | Deduplicate the source or make `ON` unique |
| Untyped NULL keeps type NULL | `CREATE TABLE t AS SELECT NULL AS x` makes a `"NULL"` column that rejects later values | `NULL::VARCHAR AS x`; revert `SET legacy_disable_null_type = true;` |
| `preserve_identifier_case` BOOLEAN -> VARCHAR | Boolean configs need translating | `'preserve_case'` (default, was `true`), `'lowercase'` (was `false`), `'uppercase'` (new, PEG only) |
| S3 URL parameters disabled | `?s3_access_key_id=...` becomes part of the object key | Use secrets; legacy opt-in after `LOAD httpfs`: `SET s3_enable_deprecated_url_parameters = true;` |
| Removed settings | `custom_profiling_settings`, `enable_http_logging`, `http_logging_output` fail | `tracked_metrics`; `CALL enable_logging('HTTP')` + `duckdb_logs_parsed('HTTP')` |
| `profiling_mode` deprecated | Setting has no effect; detailed metrics always collected | Drop it; use `enable_profiling` + `tracked_metrics` |
| ICU library removed from the core build | Custom builds no longer bundle ICU | The `icu` extension now implements time zones, calendars and collations natively; queries unchanged |
| C API v2 | Revamped, not yet stable | Rebuild extensions; expect interface changes |
| Python client | Requires Python 3.11+; result/relation API changes | See `references/language-integrations.md` |
| Delta: `delta_column_mapping_policy` default `strict` (was `lenient` in 1.5) | Column-mapped Delta tables may fail to read | `SET delta_column_mapping_policy = 'lenient';` |
| `SHOW my_table` deprecated | Prints a warning | `DESCRIBE my_table;` |

Other 2.0 changes from release-note titles (detail unsourced -- test, don't assume): DECIMAL auto-promotes past the BIGINT boundary; HUGEINT SUM/AVG overflow now throws; a warning when `OFFSET` is used without a defined ordering; the default database was removed; non-idempotent HTTP requests are no longer retried; filename and Hive-partition column collisions are rejected.

**Parser strictness (PEG):** clause order is strict (`SELECT * WHERE true FROM range(1);` is a syntax error), `SELECT` is reserved, `AND` binds tighter than `OR`, `ORDER BY true` is rejected. Error messages carry precise source locations. A reliable syntax check is `SELECT json_serialize_sql('SELEC 42')::JSON->>'error';` (the autocomplete extension's `check_peg_parser()` is unreliable in 2.0.0).

### Quack client-server protocol and CONNECT

> Source: https://duckdb.org/docs/2.0/quack/overview.html
> Source: https://duckdb.org/docs/2.0/sql/statements/connect.html
> Source: https://duckdb.org/quack/faq

```sql
-- Server
CALL quack_serve(token = 'my_token');          -- binds quack:localhost:9494
-- Client
ATTACH 'quack:localhost' AS qk (TOKEN 'my_token');
CONNECT qk;          -- unqualified SQL now runs remotely
DISCONNECT;
-- CONNECT also targets PostgreSQL/MySQL with remote pushdown:
CONNECT 'postgres:dbname=mydb host=localhost';
```

CLI: `duckdb -serve`, `duckdb -connect`. 2.0 ships a "polished" Quack, but the Quack FAQ still says beta and protocol not yet stable -- do not call it stable. Non-local servers serve HTTPS with a self-signed certificate; production needs a TLS-terminating reverse proxy. Full detail: `references/quack.md`.

### Asynchronous I/O

> Source: https://duckdb.org/docs/2.0/data/io.html
> Source: https://duckdb.org/docs/2.0/guides/performance/how_to_tune_workloads.html

On by default for Parquet, uncompressed seekable UTF-8 CSV and native DuckDB storage (including through DuckLake); JSON stays synchronous. Biggest gains on object storage.

| Setting | Default | Meaning |
|---|---|---|
| `async_threads` | 4 x CPU cores, max 256 | I/O pool, separate from `threads` |
| `read_ahead_depth` | `-1` | unlimited, bounded by the memory manager; `N` = at most N jobs ahead (no memory budget); `0` = off |
| `http_client_pool_capacity` | automatic (max 256) | `RESET` restores automatic sizing |
| `fsync_mode` | `STANDARD` | `FULL`, `NONE` |

- Never raise `threads` to speed up Parquet/seekable-CSV reads on 2.0 -- tune `async_threads` and `read_ahead_depth` if bandwidth is not saturated.
- Raise `threads` to about 2-5x cores only for synchronous formats (JSON, compressed CSV).
- The async pool is per database instance: with many instances in one process, set `threads` and `async_threads` explicitly.
- Parquet async parallelism needs at least as many row groups as threads.

### VARIANT, fully integrated

> Source: https://duckdb.org/docs/2.0/sql/data_types/variant.html
> Source: https://duckdb.org/docs/2.0/sql/functions/variant.html

```sql
SELECT '{"a":1}'::JSON::VARIANT AS v;
SELECT data.name, variant_extract(data, 'name'), variant_typeof(data) FROM events;
SET variant_minimum_shredding_size = -1;        -- disable shredding (default 30000 rows/row group)
COPY events TO 'events.parquet' (FORMAT parquet, SHREDDING {'data': 'STRUCT(name VARCHAR, age INTEGER)'});
```

- New in 2.0: shredding inside DuckDB database files (common structure stored as typed columns), shredded execution from storage, extraction pushdown into scans, shredded Parquet read/write (auto-shredding on write follows the first row group's structure), reads Snowflake-written shredded Parquet.
- Functions: `variant_typeof`, `variant_type`, `variant_keys`, `variant_extract`, `variant_extract_string`, `variant_array_length`, `variant_exists`, `variant_contains`, `variant_comparator`, `variant_normalize`, aggregates `variant_group_object`, `variant_group_array`.
- Object keys come back sorted. A `JSON` type backed by VARIANT is planned, **not** in 2.0.

### CLI agent mode

> Source: https://duckdb.org/docs/2.0/clients/cli/agent_mode.html
> Source: https://duckdb.org/2026/10/09/agent-mode.html

Turns on automatically when a known agent env var is set (`AI_AGENT`, `CLAUDECODE`, `CODEX_CI`, `CURSOR_AGENT`, `GEMINI_CLI`, `COPILOT_AGENT` and others), stdout is not a terminal, and no output-format flag is passed. Force with `-agent` / `-no-agent` or `DUCKDB_AGENT_MODE=1|0`.

- Compact Markdown tables with column types; full results up to 1,000 rows / 10,000 bytes, otherwise first and last rows plus a count; cells cut at 500 chars (`.maxrows`, `.maxbytes`, `.maxcellwidth`).
- Errors as JSON on stderr; compact EXPLAIN; a planner estimate on stderr for statements expected to read 1M+ rows.
- Pair it with `SET max_execution_time = <ms>;` to stop runaway queries.

### Triggers

> Source: https://duckdb.org/docs/2.0/sql/statements/create_trigger.html

```sql
CREATE TRIGGER trg_audit AFTER UPDATE ON target
REFERENCING OLD TABLE AS o NEW TABLE AS n
FOR EACH STATEMENT
    INSERT INTO audit SELECT n.id, o.val, n.val FROM o JOIN n ON o.id = n.id;

DROP TRIGGER IF EXISTS trg_audit ON target;     -- table name required
SELECT * FROM duckdb_triggers();
```

- `BEFORE` / `AFTER` on `INSERT`, `UPDATE [OF col]`, `DELETE`; `FOR EACH ROW` (`NEW` / `OLD`) or `FOR EACH STATEMENT` (transition tables via `REFERENCING`); one SQL statement per trigger; multiple triggers per event fire in creation order.
- **Not supported in 2.0:** `BEFORE ... FOR EACH ROW`; `UPDATE ... FOR EACH ROW`; `INSTEAD OF`; triggers on views; temporary triggers; mixing row and statement granularity for one event; `RETURNING` / `ON CONFLICT` on tables with row triggers.
- **`MERGE INTO` fails on tables with triggers.** `INSERT ... ON CONFLICT`, `INSERT OR REPLACE` and `INSERT OR IGNORE` run as a merge, so they fail on tables with UPDATE or DELETE triggers. Check this before adding a trigger to an upserted table.

### Extensibility: custom repositories and C API v2

> Source: https://duckdb.org/docs/2.0/extensions/extension_repositories.html
> Source: https://duckdb.org/docs/2.0/operations_manual/securing_duckdb/securing_extensions.html

```sql
SET allow_extension_repositories = 'allowed';     -- default 'undecided'; not persisted
CREATE EXTENSION REPOSITORY my_repo WITH PREFIX 'https://extensions.example.org'
    USING PUBLIC KEY '-----BEGIN PUBLIC KEY----- ...';
INSTALL AND LOAD my_ext FROM my_repo;             -- later sessions: LOAD my_ext FROM my_repo;
SELECT repository_name, prefix, key_fingerprints FROM duckdb_extension_repositories();
DROP EXTENSION REPOSITORY my_repo;
```

- The announcement calls this work in progress whose syntax may change. Variants: `CREATE OR REPLACE`, `IF NOT EXISTS`, `USING PUBLIC KEYS 'k1', 'k2'` (key rotation).
- Without `USING PUBLIC KEY`, keys are fetched once from `<prefix>/.well-known/duckdb-extension-repo.json`, pinned, and their SHA-256 fingerprints printed -- verify them out of band.
- Custom-repo extensions never autoload, plain `LOAD my_ext;` cannot find them, and `UPDATE EXTENSIONS` skips them (use `FORCE INSTALL my_ext FROM my_repo;`).
- `INSTALL AND LOAD` is new 2.0 syntax (the legacy parser rejects it).
- C API v2: versioned spec with per-symbol stability tags, exposes file systems and table functions to extensions, **not yet stable**. Extensions on the C++ API must be rebuilt for every DuckDB release; C++17 is required.

### Core extension updates

> Source: https://ducklake.select/docs/stable/duckdb/migrations/upgrading_to_ducklake_1_1.html
> Source: https://duckdb.org/docs/2.0/core_extensions/iceberg/iceberg_options.html
> Source: https://duckdb.org/docs/2.0/core_extensions/delta.html

- **DuckLake 1.1** (new spec + reference implementation) requires DuckDB 2.0.0+. It reads and writes 1.0 catalogs without migration. Migrating is **one-way**: back up, then `ATTACH 'ducklake:meta.ducklake' AS lake (AUTOMATIC_MIGRATION true);`. Nested schemas and the `"NULL"` type need the 1.1 format. Pinning the catalog format does not pin the DuckDB metadata file's storage version: a 2.0 client can make a DuckDB-file catalog unreadable to 1.x clients, so keep all clients on one release or use a PostgreSQL/SQLite catalog.
- **Iceberg:** new REST-catalog `ATTACH` options `DEFAULT_TABLE_LOCATION_FROM_NAMESPACE`, `USE_METADATA_LOCATION`, `PREFIX`, `NAMESPACE_SEPARATOR`; `URI` is canonical (`ENDPOINT` is a deprecated alias). UPDATE/DELETE/MERGE are merge-on-read only.
- **Delta:** `CREATE TABLE` (partitioning, table properties), timestamp time travel, VARIANT columns. `delta_column_mapping_policy` now defaults to `strict`.

## SQL Dialect Additions

> Source: https://duckdb.org/docs/2.0/sql/query_syntax/with.html
> Source: https://duckdb.org/docs/2.0/sql/query_syntax/from.html
> Source: https://duckdb.org/2026/10/26/gems-of-duckdb-200.html

```sql
-- Data-modifying CTEs (INSERT/UPDATE/DELETE/COPY ... TO); MATERIALIZED when later parts depend on it
WITH moved AS MATERIALIZED (DELETE FROM staging RETURNING *)
INSERT INTO archive SELECT * FROM moved;

-- $variable shorthand for getvariable(); unset $var raises an error (getvariable returns NULL)
SET VARIABLE threshold = 100;
SELECT * FROM orders WHERE amount > $threshold;
-- Named prepared-statement parameters fall back to same-named session variables
PREPARE q AS SELECT $threshold * 2;  EXECUTE q;  EXECUTE q(threshold := 5);

-- Nearest-neighbor joins (example form from the docs; formal grammar not captured)
SELECT q.user_id, t.product_id
FROM users q INNER JOIN products t APPROX NEAREST 2
    BY SIMILARITY array_cosine_similarity(q.embedding, t.embedding);

-- Explicit physical join type
SELECT * FROM a JOIN BY (TYPE semi) b ON a.id = b.id;

-- Nested schemas
CREATE SCHEMA finance.reports;
CREATE TABLE finance.reports.q3 (revenue DECIMAL);

-- JSON mutation (value argument is JSON text)
SELECT json_set('{"a": 1}', '$.b', '2');          -- {"a":1,"b":2}; also json_insert/json_replace/json_remove

-- Standard pagination, GROUP BY UNNEST, sequences, regex options, secure views, settings via SHOW
SELECT * FROM t ORDER BY id OFFSET 10 ROWS FETCH NEXT 5 ROWS ONLY;
SELECT unnest(tags) AS tag, count(*) FROM posts GROUP BY unnest(tags);
SELECT setval('serial', 42);                     -- next nextval returns 43; setval(..., 42, false) -> 42
SELECT regexp_extract('ABC', 'abc', 'i');        -- options overload, no capture group needed
CREATE SECURE VIEW users AS SELECT username FROM all_users;   -- stats/plans do not leak base data
SHOW threads;                                    -- prints a setting when no table has that name
```

- `JOIN BY (TYPE ...)` accepts `inner, left, right, full, semi, anti, right_semi, right_anti, mark, single`.
- Expression statements need no `SELECT` (`date: current_date();`).
- Recursive CTEs with `USING KEY`: `UNION` and `UNION ALL` now differ (`UNION` forwards only new or changed keys); payload aggregates such as `USING KEY (a, avg(b))`; the setting `deprecated_using_key_syntax` was removed. The recursive-CTE engine was rewritten.
- `MERGE INTO` cannot affect a target row twice (error); `UPDATE ... FROM` updates each target row once using an arbitrary matching source row -- deterministic only if each target matches at most one source row.

## COPY, Parquet and File-Format Additions

> Source: https://duckdb.org/docs/2.0/data/partitioning/partitioned_writes.html
> Source: https://duckdb.org/docs/2.0/data/parquet/overview.html
> Source: https://duckdb.org/docs/2.0/data/csv/overview.html

```sql
-- Custom partition paths (relative, no '..', distinct per partition; requires PARTITION_BY)
COPY sales TO 'sales' (FORMAT parquet, PARTITION_BY (region),
    PARTITION_PATH CASE WHEN region = 'eu' THEN 'europe' ELSE 'region=' || coalesce(region, 'unknown') END);
-- Sort before writing (within each partition when combined)
COPY orders TO 'orders' (FORMAT parquet, PARTITION_BY (year, month), ORDER_BY (amount DESC NULLS LAST));
-- GeoJSON writers
COPY (SELECT 'POINT(0 1)'::GEOMETRY AS geom, 10 AS f) TO 'out.json' (FORMAT GEOJSON);   -- or GEOJSONL
```

- Helpers: `hive_partition_component(name, value)`, `path_join(...)`.
- `read_parquet` new options: `allow_empty`, `bound_schema`, `int96_as`, `prefetch_strategy`, `utf8_validation`; virtual column `file_row_group_number`; Parquet page indexes read and written; COPY option `DATA_PAGE_SIZE_LIMIT`. Default Parquet compression is still Snappy.
- `read_csv` new options: `allow_empty`, `rejects_line_size_limit`.
- Row-group pruning now covers structs, lists, decimals, UUIDs, `IN` filters and function predicates such as `contains()`.

## ART Indexes in 2.0.0

> Source: https://duckdb.org/docs/2.0/guides/performance/indexing.html

ART indexes are **not** buffer-managed in 2.0.0, although the release notes list "Buffer managed indexes" PRs: those are groundwork only. Index buffers are never evicted under memory pressure, and an index must fit in memory at creation. Mitigation: `DETACH` + `ATTACH` (index memory is deserialized lazily). 2.0 does add incremental row-id remapping at checkpoint vacuum for tables with ART indexes.

## Upgrade Checklist (1.4 / 1.5 -> 2.0)

> Source: https://duckdb.org/docs/2.0/operations_manual/migration.html

1. **Inventory every process that touches each database file.** If any stays on 1.x, pin `storage_compatibility_version` (or `STORAGE_VERSION` / `-storage-version`) on the 2.0 side *before* it creates files.
2. **Back up with the old binary:** `EXPORT DATABASE 'backup' (FORMAT PARQUET)`.
3. **Stand up a shadow 2.0 system** that mirrors the workload. Mission-critical: wait for 2.0.1.
4. **Grep queries for 2.0 hazards:** `->` lambdas, `~` / `!~`, `!` factorial, `X'..'` / `B'..'` literals, integer `//` and `%` that may divide by zero, `CREATE TABLE AS SELECT NULL`, MERGE sources with duplicate keys, `SHOW <table>`.
5. **Check transaction-handling code:** after any error inside `BEGIN ... COMMIT`, issue `ROLLBACK`.
6. **Update config:** drop `custom_profiling_settings`, `enable_http_logging`, `http_logging_output`, `profiling_mode`; convert boolean `preserve_identifier_case`; replace S3 URL query parameters and `SET s3_*` with secrets; replace `PRAGMA x = y` with `SET x = y`.
7. **Clients:** Python needs 3.11+ and has API breaks; Go moves to `github.com/duckdb/duckdb-go/v2` (`v2.20000.0` = DuckDB 2.0.0); C++ API users need C++17 and lose `Connection::CreateScalarFunction` / `CreateVectorizedFunction` / `CreateAggregateFunction`. For Node, Java, Rust, R and WASM no official 2.0 migration notes exist -- test.
8. **Extensions:** `UPDATE EXTENSIONS;`. Community extensions publish a per-version/platform compatibility matrix -- check each one. Rebuild in-house C++-API extensions.
9. **DuckLake:** upgrade catalogs to 1.1 only after every client is on 2.0 (migration is one-way).
10. **Escape hatches while porting:** `enable_legacy_parser`, `lambda_syntax = 'enable_single_arrow'`, `legacy_disable_null_type`, `default_transaction_invalidation_policy`, `error_on_division_by_zero = false`. Treat each as temporary.

## Deprecations and Planned 2.1 Removals

> Source: https://duckdb.org/roadmap
> Source: https://duckdb.org/docs/2.0/configuration/overview.html

- **Removed in 2.1 (roadmap):** the `lambda_syntax` setting and single-arrow lambda syntax; `osx_amd64` support (2.0 still builds core extensions for it; community extensions are best-effort).
- **Deprecated in 2.0:** amalgamation builds; `profiling_mode`; `regex_match_operator_semantics`; `SHOW <table>`; `PRAGMA name = value` assignments; `enable_object_cache` (does nothing); legacy `s3_*` settings (`s3_access_key_id`, `s3_secret_access_key`, `s3_region`, `s3_endpoint`, ...); `extension_directory` (use `extension_directories`); implicit table-function identifier-to-string conversion.
- **Planned, not in 2.0.0:** `JSON` type backed by VARIANT; buffer-managed ART indexes. The preview post's `MMAP` / `DIRECT_IO` I/O modes are not documented for 2.0 -- do not recommend them.
