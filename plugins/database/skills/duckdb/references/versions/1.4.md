# DuckDB 1.4 LTS

This reference covers DuckDB 1.4 LTS (codename "Andium"), first released September 16, 2025 -- DuckDB's first Long-Term Support release. DuckDB 1.4 introduced database encryption, the MERGE statement, Iceberg writes, and materialized CTEs by default.

**Support status (as of 2026-11-13):** previous LTS, **end of life 2026-11-17**. Support was extended from the original one-year window (September 16, 2026). The current LTS is **2.0.0** (released 2026-10-21, supported until about October 22, 2027). Plan the move off 1.4 now: either to 2.0 LTS, or to 1.5 (non-LTS, supported until 2027-03-01) as a staging step. See `references/versions/2.0.md` for the upgrade checklist.

## Key Features Introduced in DuckDB 1.4

> Source: https://duckdb.org/2025/09/16/announcing-duckdb-140.html

### Database Encryption

> Source: https://duckdb.org/docs/2.0/sql/statements/attach.html

DuckDB 1.4 encrypts database files with AES-256, GCM mode by default, covering the main database file, the WAL, and temporary files:

```sql
-- Create (or open) an encrypted database
ATTACH 'secure.duckdb' AS secure (ENCRYPTION_KEY 'my_secret_key_here');

CREATE TABLE secure.main.sensitive_data (id INTEGER, ssn VARCHAR, name VARCHAR);
INSERT INTO secure.main.sensitive_data VALUES (1, '123-45-6789', 'Alice');

-- Detach and reattach: the key is required to open
DETACH secure;
ATTACH 'secure.duckdb' AS secure (ENCRYPTION_KEY 'my_secret_key_here');

-- Choose a cipher explicitly (CBC, CTR or GCM; GCM is the default)
ATTACH 'other.duckdb' AS other (ENCRYPTION_KEY 'k', ENCRYPTION_CIPHER 'CTR');
```

Never write `ENCRYPTION_CONFIG {key: ...}` -- that option does not exist; the documented options are `ENCRYPTION_KEY` and `ENCRYPTION_CIPHER`.

**Implementation details:**
- Algorithm: AES-256, GCM by default (CBC, CTR selectable)
- Coverage: main file, WAL, temp files (2.0 also lists a `temp_file_encryption` setting, default `false`; set it explicitly if temp-file encryption matters)
- Requires storage version 1.4.0 or later
- Backends: built-in mbedtls (default), or OpenSSL via `httpfs` -- much faster thanks to hardware acceleration

```sql
-- Load httpfs BEFORE attaching to get the OpenSSL backend
LOAD httpfs;
ATTACH 'fast_encrypted.duckdb' AS fast (ENCRYPTION_KEY 'key123');
```

**Best practices:**
- Keep keys in a secrets manager, never in source code or committed SQL scripts.
- Load `httpfs` first for workloads that read/write encrypted databases heavily.

### MERGE Statement

> Source: https://duckdb.org/docs/2.0/sql/statements/merge_into.html

DuckDB 1.4 adds MERGE INTO, the SQL-standard upsert. It needs no primary key -- the `ON` condition is arbitrary:

```sql
-- Basic upsert
MERGE INTO orders AS target
USING staging_orders AS source
ON target.order_id = source.order_id
WHEN MATCHED THEN
    UPDATE SET amount = source.amount, status = source.status
WHEN NOT MATCHED THEN
    INSERT (order_id, customer_id, amount, status)
    VALUES (source.order_id, source.customer_id, source.amount, source.status);

-- Conditional actions, including DELETE
MERGE INTO inventory AS target
USING updates AS source
ON target.product_id = source.product_id
WHEN MATCHED AND source.action = 'delete' THEN DELETE
WHEN MATCHED AND source.action = 'update' THEN
    UPDATE SET qty = source.qty, price = source.price
WHEN NOT MATCHED AND source.action = 'insert' THEN
    INSERT BY NAME;

-- Whole-row forms from a file source
MERGE INTO orders AS target
USING read_parquet('updates.parquet') AS source
ON target.order_id = source.order_id
WHEN MATCHED THEN UPDATE
WHEN NOT MATCHED THEN INSERT BY NAME;
```

Use the documented whole-row forms `WHEN MATCHED THEN UPDATE` and `WHEN NOT MATCHED THEN INSERT BY NAME`; `UPDATE SET *` / `INSERT *` are not documented. The current docs also show `WHEN NOT MATCHED BY SOURCE THEN DELETE` and `RETURNING`.

**Upgrade hazard:** in 2.0, a target row matched by more than one source row in an UPDATE/DELETE branch raises an error (`MERGE INTO command cannot affect the same target row more than once`). Deduplicate the source or make the `ON` condition unique before upgrading.

### Iceberg Writes

> Source: https://duckdb.org/2025/09/16/announcing-duckdb-140.html
> Source: https://duckdb.org/docs/2.0/core_extensions/iceberg/writing_to_iceberg.html

DuckDB 1.4's iceberg extension added writes to Iceberg tables through an attached REST catalog:

```sql
INSTALL iceberg;
LOAD iceberg;

-- Copy an Iceberg catalog into a DuckDB database (direction shown in the 1.4.0 post)
COPY FROM DATABASE iceberg_datalake TO duckdb_db;
```

- Writing requires an attached catalog; tables read directly with `iceberg_scan` are read-only.
- Copying *into* Iceberg requires creating the target schemas first.
- Later lines extended this: 1.5.3 added Iceberg `MERGE INTO`, partitioned INSERT/UPDATE and `ALTER TABLE`; 2.0 adds REST catalog `ATTACH` options. On 2.0, UPDATE/DELETE/MERGE are merge-on-read only.

### Materialized CTEs by Default

> Source: https://duckdb.org/docs/2.0/sql/query_syntax/with.html

In DuckDB 1.4, Common Table Expressions are materialized by default instead of inlined:

```sql
-- The CTE is materialized and reused
WITH expensive_calc AS (
    SELECT region, sum(amount) AS total FROM orders GROUP BY region
)
SELECT * FROM expensive_calc WHERE total > 10000
UNION ALL
SELECT * FROM expensive_calc WHERE total < 1000;

-- Explicit hints exist but the docs advise against them in general
WITH cheap_filter AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE status = 'active'
)
SELECT * FROM cheap_filter LIMIT 10;
```

Materialization is the default, not a guarantee: DuckDB can still inline a CTE when its heuristics allow (e.g. `AS NOT MATERIALIZED`), and "Generally, it is not recommended to use explicit materialization hints."

### COPY FROM DATABASE

> Source: https://duckdb.org/docs/2.0/operations_manual/migration.html

```sql
-- Copy an entire database into another attached database
ATTACH 'target.duckdb' AS target;
COPY FROM DATABASE memory TO target;
```

Also the documented way to convert a file to an older storage version (see the storage section of `references/versions/2.0.md`).

## LTS Support Model

> Source: https://duckdb.org/release_calendar

- **LTS releases:** starting with 1.4.0, every other DuckDB version is LTS (1.4, then 2.0).
- **Support duration:** community support "currently lasts one year after release"; 1.4 was extended to 2026-11-17.
- **Non-LTS releases:** normally supported until the next minor release; 1.5 is the exception (extended to 2027-03-01).

**Storage compatibility:** DuckDB 1.0 through 1.5 write storage version 64 by default, so 1.4 and 1.5 files are interchangeable. DuckDB 2.0 reads and writes 1.4 files without changing their version -- but files **created** by 2.0 use storage version 69, which 1.4 cannot open.

## Migration from Pre-1.4 Versions

> Source: https://duckdb.org/2025/09/16/announcing-duckdb-140.html

1. **CTEs are materialized by default** -- queries that relied on inlining may perform differently.
2. **Extension compatibility** -- extension binaries are built per DuckDB version. Run `UPDATE EXTENSIONS;` after upgrading.
3. **Back up first** -- forward compatibility is best effort only.

```bash
# 1. Back up the existing database with the OLD binary
duckdb old_version.duckdb "EXPORT DATABASE 'backup' (FORMAT PARQUET)"

# 2. Install DuckDB 1.4 (latest patch: 1.4.5)
pip install duckdb==1.4.5

# 3. Update extensions and verify
duckdb my_database.duckdb "UPDATE EXTENSIONS;"
duckdb my_database.duckdb "SELECT version(); PRAGMA database_size;"
```

## When to Choose DuckDB 1.4 LTS (as of November 2026)

> Source: https://duckdb.org/release_calendar

Choose 1.4 only to finish an in-flight rollout before 2026-11-17. For anything new:
- **2.0 LTS** -- current LTS; supported until about October 2027.
- **1.5** -- if you need a 1.x line past 1.4's EOL (supported until 2027-03-01) while you test 2.0.
